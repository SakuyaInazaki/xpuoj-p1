## 1. 总目标

**总目标 [A]**：在 2026-10-01 23:59（UTC+8）前，使三题「罚分后的最高分」之和最大化。每题满分 100（测试点平均），三题合计理论上限 300。

**总目标的量化表达**：

| 指标 | 目标值 | 测量方法 |
| --- | --- | --- |
| 三题总分 S_total | ≥ 240（平均每题 ≥ 80） | 平台排行榜（以 XPUOJ 评测机返回结果为准 [A]） |
| 每题得分 S_i | 赛题二、三 ≥ 85；赛题一 ≥ 75（赛题一通信/环境不确定性更高，见风险表） | 平台提交返回 + 本地分数估算器（workflow.md §4.3） |
| 正确性 | 三题全部测试点通过约束校验（SQNR、有限性、输入不可变、确定性） | 本地验证脚本 + 平台提交 |
| 提交预算 | 每题平台评测提交 ≤ 60 次（100 次限额内留 40 次余量，超限罚分公式见 background.md §1.4） | 平台提交历史记录 |
| 复现性 | 最终提交在 3 次本地重复测量中，平均时间标准差/均值 ≤ 2% | 本地计时 harness（workflow.md §3.1） |

**分数-时间换算锚点（由题包公式 [A] 推导，s=0.5，T_k>T_h 区间）**：

```
Score = floor(100 / (1 + (T_k − T_h)/(T_b − T_h)))
```

- T_k = T_b → 50 分；T_k = T_h → 100 分；
- 得分 ≥ 85 ⟺ T_k ≤ T_h + 0.176·(T_b − T_h)（即：T_k 距 T_h 不超过「T_b 到 T_h 区间」的 17.6%）；
- 得分 ≥ 90 ⟺ T_k ≤ T_h + 0.111·(T_b − T_h)；得分 ≥ 95 ⟺ T_k ≤ T_h + 0.0526·(T_b − T_h)。

> 推论：目标分数越高，对「逼近 T_h」的要求越苛刻。85 分≈「把 baseline 的 82% 以上时间省掉」；95 分≈「省掉 95% 以上」。本目标设定为二、三题 85+、一题 75+，是「逼近 T_h 约 12%~18% 区间」的可达目标，95+ 作为冲刺项（M4）。

**题目级目标速比（本地可测的代理指标）**：在 T_h 口径 [C] 未知时，以本地实测 T_b（自建朴素参考）与 T_k 的比值代理：

| 赛题 | 目标 T_k/T_b（本地代理） | 对应分数（估算，假设 T_h ≈ 0.1·T_b） | 备注 |
| --- | --- | --- | --- |
| 一 MegaMoE | ≤ 0.30 | ≥ 75 | 通信+计算融合，分布式环境波动大 |
| 二 MagiAttention | ≤ 0.22 | ≥ 85 | 内存/计算混合受限，mask 优化空间大 |
| 三 mHC | ≤ 0.25 | ≥ 85 | 内存受限，融合核是命门 |

> [C] 提醒：上述「对应分数」依赖 T_h 假设，实际以平台 T_b/T_h 校准（workflow.md §0.3）；**T_k/T_b 是本地唯一可复现的代理指标，所有里程碑以它为准**。

## 4. 每阶段验证方法与成功判据（细目）

### M0：前置确认（成功判据全为「拿到事实」）
1. 报名成功、能读三题题目详情 [C]：run_kernel 签名、测试点配置（维度表）、baseline 说明、T_b/T_h（若有）。
2. 平台评测环境版本清单 [C]：CUDA（<12.6）、PyTorch、Triton 版本、Triton-distributed 版本、NVSHMEM 版本；本地环境按同版本搭建。
3. 赛题一评测方式确认 [C]：4 进程启动方式、对称内存分配、是否允许预热预处理。
4. 校准提交：P2/P3 各提交一版朴素正确实现（≈T_b 水平），确认 >0 分且拿到真实 T_b 感觉；P1 待评测方式确认后提交最小正确实现。
   - 判据：4 项全部完成，版本清单写入 `REPRO.md`。

### M1：正确性基线（判据全部量化）
1. 参考实现（本地）：P2 用 FP32 朴素 slice+合并+sink；P3 用 FP32 逐 token 朴素（Sinkhorn 20 迭代）；P1 用 FP32 单卡等价 + 4 卡一致性核对。
2. 验证脚本四连：SQNR 达标（阈值+5 dB）、有限、输入不变、确定性——全绿。
3. 平台提交朴素正确实现，返回 >0 分。
   - 判据：上述全部通过；若 SQNR 不达标，优先排查（P2: BF16 中间量；P3: Sinkhorn 精度/顺序；P1: 归约顺序、路由索引类型），不允许带病进入 M2。

### M2：v1 优化（判据：T_k/T_b ≤ 0.50 且约束全绿）
- P2：FA2 级 Triton kernel（可先忽略部分 mask 优化，先正确）；Triton autotune 固定最优配置。
- P3：论文 3 核方案落地（系数 GEMM 融合 φ、RMSNorm 重排、权重吸收、F_post,res 融合）。
- P1：官方 `test_ep_moe_inference.py` 移植为赛题 run_kernel；路由索引改稳定排序（保确定性）；固定编译参数。
- 每项改动后：①约束四连全绿；②计时 harness 记录 T_k；③分数估算器出分。
- 判据：达标即进入 M3；未达标时对照调研表逐项排查（background.md §5）。

### M3：v2 优化（判据见 §3 表）
- P2：预热期静态 solver（mask→block 迭代表）；slice 级并行 + 确定性 LSE 归约；sink 后处理融合；GQA KV 复用打包。
- P3：persistent 单核（x 读写各一次）；Sinkhorn 压入 warp 寄存器；低秩 GEMM + SiLU epilogue。
- P1：`ep_all2all_fused` 式 fused megakernel（dispatch/combine 与 GEMM 重叠）；per-expert 对齐；必要时虚拟专家。
- 判据：T_k/T_b 达标 + 约束全绿 + 复现性 ≤ 2%。

### M4：冲刺调优（判据：T_k/T_b 再降 ≥ 10% 或分数估算器到 90+）
- 参数扫描（BLOCK_M/N/K、num_warps、num_stages、切片策略）；P2 尝试 warp_specialize/TMA；P1 通信与计算的比例调优、缓冲大小。
- 极端 case 加固：P2 的 lse=−inf 行/sink 极值；P3 的小 T 延迟场景；P1 的 token 分布极端不均。
- 数值余量核查：SQNR 余量 < 5 dB 时先查精度问题，不得靠运气提交。
- 判据：性能目标达成且所有约束仍全绿；若冲刺项（P2 90+）两周内无法达成，接受 85 分档，进入 M5。

### M5：复现与终局（判据见 §2 总表）
- 冻结代码与版本；3 次重复测量（std/mean ≤ 2%）；归档 benchmark 日志；最终提交。
- 判据：最终提交三题 ≥ 240 分、每题 ≤ 60 次提交；所有存档可复现。

| R11 | 平台复核（正确性/性能/确定性/原创性） | 中/中 | ①代码原创、不搬运他人提交 ②执行确定性（固定编译参数）③保存完整实验记录与 REPRO.md ④不做任何绕过评测的行为（题包参赛规范 [A]） |
