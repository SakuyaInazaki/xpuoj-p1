## 3. 不能一刀切关闭的组合负结果

### 3.1 输出 TMA：现成的正信号仍在，但必须把映射成本拿掉

`experiments/2026-09-13/SUMMARY.md:7-9` 区分了三个实验：

1. TMA + 原 flatten 的第一份代码编译失败，无性能读数。
2. TMA + candidate no-flat 数学全过，但 DN+gather 慢 14.35–14.60%，关闭这个组合。
3. 两边保留 flatten、候选全 tile 写 padded C8：初测 DN 快 2.80–3.18%；六组确认本体全快，范围 2.52–5.52%，ratio of means 对应降时 3.98%。计入独立 PAD_ROW 构建和二级 gather 后总体 1.000875×，三快三慢。

所以失败项是“独立 map 构建 + dependent mapping load 抵消 DN 收益”，不是“输出 TMA 一定慢”。`docs/STATE.md:85-86` 明确保留消除准备/索引税后重启的边界。

### 3.2 MD flatten：不是所有 flatten 都被否定

`docs/STATE.md:102-105` 记录：简单开 flatten 慢 104–142%，三向量 load 下沉配合 flatten 却在 c11/c12 稳定赢 2.5–3.4%，已晋升 v830；推广到其他家族慢 1.2–18%。应保留 c11/c12 现有实现，拒绝再次照抄推广。不同 metadata 活跃区间可改变结果，但必须有实际 IR/资源差异而非换名。

### 3.3 launch 融合的历史关闭很多是“收益不可分辨”，不是执行过全图最优证明

旧 v323 融合排序已经正确且确定，最终测量落在当时高噪声内，见 `archive/handoffs/handoff-session-20260821/session-notes.md:594-614`。不能由此断言任何排序算法都无空间；也不能因统计方法改善就重发同码几十次。新方案必须减少实际执行、临时矩阵或内存依赖，不能只以“少三个 launch”立项。

## 4. 证据与噪声：后续实验应换成更严格、更少提交的协议

- **保留 raw tk 与 tb，优化判断只依 tk。** `docs/STATE.md:261` 的 best 刷新来自三处 tb 异常；`knobs9.md:272` 的某次 c4 越线也不能挽救该配置最终均值 −0.035%。单次分数过线不等于性能提升。
- **不要直接复用老 mnorm 签名。** `docs/STATE.md:279` 给出新旧机器系数差异；`c910_replicate.md:138-145` 的空白对照 c9 残差 sd=1.07%、corr(m,resid)=0.40。其误差尺度足以伪造多个“1% 优化”。
- **用最新同代码路径的 anchor 池，先声明触碰集合。** `strat.py:14-23` 和 `strat6.py:12-29` 提供分层/配对 dM 校正范式；不能直接把脚本硬编码的 v837/v838/v841 池与控制集合搬到未来变化的底盘。
- **池化不会自动消除机器混杂。** 候选和锚的机器分布不同，raw 池均值仍会偏。需与随机交替配对、fresh anchor 回归同向；两者冲突先解释，不能挑有利估计器。
- **优先固定确认批，不持续观察到 z 过线即停。** 09-20 有按首轮赢家分配后续样本和逐次看 z 的过程；适合作筛选，最终提效幅度仍应以独立冻结 SHA 的确认批为准。多个候选、多个 case、多个估计器也存在选择偏差。
- **不要把“SQNR 输出字符串相同”写成输出逐位相同。** 日志通常只有小数点后两位；平台 AC/确定性和 baseline-vs-candidate bitwise equality 是不同门。调 launch 参数可保数学，但仍需候选直接比较证据才能称逐位一致。
- **分清单卡、阶段和 P1 全链。** c4 padded custom 的解析路由、rank0 EP events、常量 INT4 指令探针都只支持各自范围。单卡初筛可以关闭明显失败，但正收益必须完整链确认。
- **500 秒 TLE 与性能必须分离。** 新 JIT 源和样例槽 TLE 有相关性记录（STATE:192-209、248），但补充官方说明已确认是 torchrun 总预算；没有 PTXAS/阶段时间日志就不能定论为特定 kernel 冷编译。“只要新内核就不可能”也被 EP 七个小新内核成功反证（ep_build:90-91）。先对精简 module 做离线编译与合法单卡 custom，完整 P1 再核实总预算；只有 TLE 的路线标为“未完成验证”，不能写成速度判负。
- **诊断可用性先验证，不绕过拦截。** 旧 event 成功与新参赛者拒绝可以同时成立。若当前 Event 不可用，阶段筛选采用平台提供的单卡 custom 完整 workload tk，通过相同 wrapper 的对照 payload 验证完整被触碰链；不用异常/字符串绕过等手段强行恢复计时接口。四卡归因只能用合法正式平台结果与允许的日志，单卡 custom 不可宣称验证了分布式性能。
- **小效应的验证预算可提前算。** `knobs11.md:53-64` 的空白对照意味着 −0.3% 在 c9/c10 需要约 96 对，在 c11/c12 约 9 对。这足以拒绝没有实际字节/指令削减的微调提案。

roofline 可用来排序机会，不能单独作为“任何算法都不可能提分”的证明。峰值、实频、实际 weight/A 复读量、padding、评分整数台阶都必须一致；旧记录已有 boost 与实频纠正（session-notes:1350-1361）。当前证据足以说明：依靠 0.3% launch 微调追数个榜分不现实。

## 5. 推荐的有界验证方向

### A. c4 padded DN 输出，直接生成 padded inverse，保留单级 gather（优先）

**为何不同于失败方案：** 09-13 候选额外建 `PAD_ROW`，fin 先查 INV 再查 PAD_ROW。尝试在既有排序/offset 阶段产生 `INV_PAD`，同时把 DN 的 CSCL 也写到 padded row。fin 直接用 `INV_PAD` 同时读取 Down 与 DSCL，消除额外构建 kernel 和 dependent map load；原 INV 保留供前面的量化/MD 使用。

**代码依据：** `p1/kernel.py:733-747` 已读取全部 expert counts，可额外计算 `pad_exc[e] = 128 * sum_{j<e} ceil(count[j]/128)`；`:694-712` 已计算每条路由的稳定 `pos`，可写 `INV_PAD[route] = pos + pad_exc[e] - unpadded_exc[e]`。DN 当前输出是 `:4566-4574`，fin 单级读是 `:4701-4709`。旧 padded 参考 `fp8_c4_dn_tma_padded_custom_bench_confirm.py:159-186,228-250`。

**最小验证：** 先写 CPU 索引性质测试，覆盖空专家、1/127/128/129 行、极端偏斜和随机路由；所有原 row 精确映射一次、padding 无冲突、容量用 `M+E*127` 的安全上界。再用一个 c4 custom 同时比较：(i)原 sort→DN→fin，(ii)额外 INV_PAD 写入的 sort→padded DN/CSCL→原结构 fin。保持 FP8 和 BF16 全输出直接比较、scale/zero/finite 门；需要明确显式 T 参数，因为 padded Down.shape[0] 已不能推导 `T=N/k`（当前 host :4716-4717）。

**继续闸门：** 完整被触碰链含索引准备需稳定改善；若仅 DN 快而全链仍中性，立即停，不扫 store/stage。先限制 c4。c6/c11/c12 只能在 c4 机制成功后分别验证，不能直接继承比例。

**限制：** 旧正信号产生于 s4，当前 c4 DN 已为 s3（v840）；必须先确认在当前启动配置下正信号尚存。新增加的 offset 算术和第二份 inverse 写流量也可能吃完收益，因此这是有证据的假设，不是已知可晋升项。

### B. 替换计数排序的局部稳定排名算法，先做纯排序上界探针（次优，低预算）

**为何不同于旧 fusion/warp 扫描：** 现役 hist 和 scatter 都物化 `[BLOCK,E_PAD]` 的 eq，scatter 再沿 token 做 cumsum（`p1/kernel.py:624-637,694-712`）。c9/c10 是 64×256，c7/c8 是 128×128；旧优化主要改变 launch 形状或融合原算法，没有证明这份局部排名算法最优。

**目标机制：** 用紧凑直方图加 warp 内同值匹配/位掩码计数生成稳定 local rank，再合并 warp 前缀，减少 eq 矩阵和全轴扫描的执行成本。可以先验证编译器是否能安全提供所需 primitive；不要假设任何 inline PTX 在当前 fork 上必然正确。整数计数可用确定的前缀，不采用依赖 CTA 到达顺序的 atomic append。

**最小验证：** 一个独立排序 custom，只覆盖 E=32/96/256，直接对照现役 sort 的 ORDER/INV/COUNTS 全元素完全相同，包含重复值、空专家、边界 chunk、偏斜分布。比较 hist+prefix+scatter 整段，不能只报 scatter。若新 primitive 编译或 layout 无法可靠验证，停。

**继续闸门：** 先取得当前完整 sort 的实际阶段成本；新方案必须消除可观比例的这部分成本，且预估端到端收益高于可接受确认预算的噪声门槛。不得以少一次 launch 或 1–2 µs 不稳读数申请几十次 P1。它也可作为 A 中生成 INV_PAD 的载体，但两项必须先单独归因。

**历史边界：** 这是“未发现同机制已测记录”，不是“确定从未有人做过”；实现前再以候选源码关键字核查。若完整 sort 成本本来很小，应降为支撑 A 的工程选项，停止独立提分线。

### C. 对只有 TLE 的结构做一次总预算/编译归因，版本路线暂缓（有条件）

补充官方说明改变了 TLE 归因。`docs/STATE.md:199-205` 的 TMA tiled/source specialization 或 c9/c10 block-interleave 只有总超时，不能视为对应结构的速度失败。**仅当某份候选具有清晰的字节/访存机制预算时**，允许从该候选抽取一个现役几何的最小 module：使用与线上匹配的 3.4 编译栈、正确 jit 装饰器，拿到 PTXAS stderr/资源和单卡正确性。工具可用时先 `triton.compile`；无兼容编译环境则用合法单卡 custom，不安装或升级生产依赖来“修复”测试环境。

最小模块通过只表明有资格进行完整 P1 验证；不代表 500 秒总预算一定足够。若下一次正式平台仍 TLE 且无新诊断信息，先向主办方索取合法日志，不原样反复重发。此方向排在 A/B 之后，也不复活已有明确慢读数的 BM64/f16/EP。

官方现已明确 3.4，版本复探不再是即时优先项。只有后续正式新镜像说明出现，才重新做 f16 lowering/低层 WGMMA 小探针，并跨过 `f16acc_bm256.md:91-95` 的原生化门槛后考虑 BM256 或 producer/consumer pipeline。

### D. 冻结 v842 的累计收益与测量工具（并行基础工作）

这是实验效率任务，不直接产生更快 kernel。把最终 v842 与明确旧基线做同窗累积验证，并固化版本、per-case 代码哈希、raw tk/tb/SQNR、候选触碰集和 fresh A/A 空白分布。旧历史出现过多次逐项晋升相加远大于累积实测（session-notes:1336-1348）；缺少这一层会继续把噪声当进展。

用固定确认批、按提交/会话整体重采样的区间，报告端到端 Δtk 和固定 tb 下的预期积分变化。不要把 6,948 个共享 anchor 构成的 pair 当 6,948 个独立样本；它们可估计 pair 分布，但统计有效样本数仍受原始 run 数约束。

## 6. 分派建议

先让一个 coding agent 做 A 的索引与单卡完整链原型；第二个做 B 的成本测量和 primitive 可行性；第三个负责 D 与独立正确性审查。C 只从一份具备结构预算、但历史仅因 TLE 未能取数的候选出发；编译器新能力分支继续等待正式更新。每项先提交一页预算和直接验收门，再生成候选；一个明晰机制一次只改一处，拒绝无目标参数扫描。

主报告不应承诺这些方向可追回 4 个榜分。现有材料更支持“保留一个具体正机制、验证一个算法缺口、等待一个外部能力变化”。记录充分的无收益结论同样能防止后续 agent 继续耗在已排除路线。
