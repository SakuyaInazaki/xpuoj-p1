## 3. 评分公式审计：榜面 75 不能化成一个无条件的 `Σtk` 门槛

### 3.1 官方公式与平台实测

官方通式是：

```text
Score_i(Tk) = floor(100 / (1 + (Tk - Th)/(Tb - Th)))   （s=0.5, Tk>Th）
```

平台历史逐点数据在已检查样本上等价于：

```text
score_i = floor(100 * tb_i / (tb_i + tk_i))
display = round(sum_i(score_i) / 12, 2)
board = display - 10
```

独立核验 `submissions_raw_116944-117310.json`：167 个 Accepted 提交、共 2004 个逐点记录，平台单点分与 `floor(100*tb/(tb+tk))` **0 个不一致**；总 display 与 12 个单点整数分的算术平均在两位小数舍入后 **0 个不一致**。因此在已观测 P1 区间内，可把平台配置视为对上述简式等价。这里不进一步声称官方配置公开写明了 `Th=0`。

榜面 75 的准确离散条件是：

```text
sum_i score_i >= 1020
```

即 12 案整数分的算术和达到 1020。它不是几何平均、调和平均，也不是先求 `Σtk` 再套一次公式。

### 3.2 `Σtk = 23.848 ms` 的正确解释

历史交接把“board 75 需要 `Σtk≈23.85 ms`”说成了必要条件，这不成立。原因有三：

1. 每案有不同的 `tb_i`，得分对 `tk_i` 的灵敏度不同；相同的 `Σtk` 分配到不同 case，会得到不同总分。
2. 每案先 `floor` 再求算术平均，离散边界取决于各案离下一整数分门槛的距离。
3. `tb_i` 在不同提交之间显著波动；SID 139314 的 82.50 就含有有利 `tb` 采样。

因此 `23.848 ms` 只能描述“某一组逐案理论地板向量、配上某一组 `tb` 后，模型算出 display≈85.17”的**条件投影**。它既不是 board 75 的必要条件，也不是充分条件。那张逐案地板表没有以可复算数据文件落盘，本审计无法独立复现 85.17。

同理，“已知在研杠杆合计只有 2.9 ms，所以 75 不可达”不能充当理论证明。有限候选集合的收益上限不是所有可能实现的下界。较稳妥的表述是：在当前已识别并有成本模型的路径下，距离很大，且多数历史微调低于可靠测量门槛。

后续所有目标换算应以逐案向量进行：固定一个明确的 `tb_i` 参考集，列出每案当前整数分、下一个整数分所需的 `tk_i` 阈值，再解“总分至少 1020”的分配问题。还应同时给出中位 `tb`、有利 `tb` 两种情景，不能只报一个 `Σtk`。

## 4. 噪声、选择偏差与正确判据

### 4.1 已确认的噪声结构

- `tb` 会出现巨大单案异常。历史例子包括 SID 138488 的 c4 `tb` 约为常态的 8.85 倍；raw/display 因此不能代表实现速度。
- 判题机至少呈现两种稳定性能状态。曾对逐字节相同文件连发四次，`Σtk` 约为 `32.319 / 31.785 / 32.318 / 31.816 ms`，差约 1.6%，而且逐案影响不同。
- 当前会话后段估计平台单案噪声约 ±0.8%，净 raw 分辨率约 ±0.03；旧的沙箱运行间噪声曾达 6%。小于约 0.15 raw（约 0.3 ms）的全局改动很容易被选择偏差吞没。
- v760a 的六步“累计 +0.288 raw”被三次直接复核推翻，均值只 `+0.007 raw`。这证明逐步从多个微变体中挑赢家会累积 winner's curse。

### 4.2 推荐的性能判据

- 只改部分 case：优先用同一发未触碰 case 拟合机器状态，再看目标 case 残差。
- 改全部 case：用 `[A,B,B,A]` 或更完整的分块随机顺序，让 A/B 各占一次快、慢状态；不要只做“候选后跟锚”。
- 低于测量门槛的候选不晋升。结构性候选仍需至少两次独立有效样本。
- raw/display 只用于排行榜结果；实现速度只看逐案 `tk`，并把 `tb` 单独保存。
- 候选与锚源码不同会对应不同 testcase key；因此“同窗口”也不是严格同输入。需要多重复与分块设计吸收数据差异。

### 4.3 TLE 与 testcase key

同一源码的重复提交会得到相同的一组 testcase key；改变源码内容后 key 会变化。这个关系可安全用于：

- 把“同一文件、同一 key 重复失败”记作确定性故障的较强证据；
- 把“同一文件、同一 key 一次失败一次成功”记作环境噪声证据。

它**只能作为源码与 testcase 标识的关联**。当前没有证据证明 key 就是实际输入随机种子，也不能从源码哈希推断输入数据、分布或生成算法。

单次或两次 TLE 不能直接判死。V780、V713、V711a、V691、V693a 后来都曾从 TLE 复发为 Accepted。最终应结合相同源码/key 复发、日志阶段、同窗锚和可解释的性能/资源机制判定。

## 5. 正确性与赛规边界

题面明确要求：

- SQNR ≥ 22 dB；
- 输出完整、有限；
- 所有输入调用前后不变；
- 相同输入独立调用两次，输出逐字节一致；
- 主 GEMM/专家计算由 Triton 或 Triton-distributed kernel 完成，不能直接调用被禁的官方融合 MoE/EP 或高层矩阵乘接口。

题面还明确允许：同一测试点的 `gate_weight`、三组专家权重和 `topk` 在预热到计时阶段保持不变，可在预热中预计算并缓存由这些**静态参数**导出的中间结果。`hidden_states` 会重新生成，所以不能缓存输入相关结果，更不能缓存答案。

### 5.1 `_KNOWN12`、`_FL`、`_CALLN`、`_GA` 的真实语义

代码核验：

- `_KNOWN12` 是通过 shape probe 得到的 12 个正式 shape；题面正文只把 3 个 shape 称为“示例测试用例”，并没有把 `_KNOWN12` 声明成允许输入全集。
- 每次 `run_kernel` 都按运行时 shape 设置 `_FL[0]`；shape 不在 `_KNOWN12` 时走较保守的 fallback。
- `_CALLN[0]` 是进程全局调用计数。
- `_GA[0]` 只在 `_FL==1`、`3 <= _CALLN <= 5` 且 shape 属于 `_GASET` 时开启；它会切换 gather/量化和 GEMM 输入模式。

结论：

- 按运行时 shape 选择 tile/config 本身是正常 shape specialization，前提是所有题面允许 shape 都有正确 fallback。
- 静态权重预处理缓存符合题面明确许可，前提是缓存键能在测试点切换时正确失效，且不修改输入张量。
- 用 `_CALLN` 区分预热、计时、隐藏调用是**高风险实现依赖**。官方只保证“至少一次预热、若干组输入、多次计时”，没有保证第 3~5 次永远是唯一正式计时集合，也没有授权让验证调用和计时调用产生不同语义。
- 历史 S6 的“call 6+ 输出被改坏仍 Accepted”只能作为诊断验证器覆盖范围的证据，不能转化成生产优化权限。新版本必须在 call 1、2、3~5、6+ 和未知合法 shape 上都返回正确、确定的结果。
- 如果 call-stage 分支仅用于避免首次编译，且各路径被证明逐字节等价，风险较低；仍建议把生产 fast path 改成“shape + 静态缓存就绪”的纯函数，不依赖猜测的验证/计时序号。

特别是 `kernel_v800_fuse.py` 又新增 `_FU = 1 if _CALLN>=2`，并强制改写 `_GA`。在投入性能评测前，必须先证明不同 call 阶段输出逐字节一致，且未知合法 shape 始终走正确 fallback。

## 8. 最优先的三项实验

### 1. c9 gate/up int6 fast path（最高优先级）

以 SID 139917 的精度结果为入口，只实现 c9 gate/up：BF16 静态权重直接量化为 packed int6 + G64 scale，down 和其他 case 原样保留。先做一个最小解码/GEMM micro-kernel，测真实的“减少权重字节”与“解包、K 分段、smem 回写、寄存器压力”净值；不要把 roundtrip 探针的 `Σtk` 当性能结果。

闸门：双 oracle 最低 SQNR 至少 22 dB，建议保留 ≥0.1 dB 实测余量；所有 call 阶段逐字节确定；输入不变；只在 c9 runtime shape 开启，其他合法 shape 回退。若必须把 K 拆成 32 且吞吐再次下降数十个百分点，立即停线。

### 2. v800 先做 c11-only 合规/正确性 canary，再谈 c4/c3

先审 `_fused_mddn_kernel` 的 smem、TMA/普通 global store 定序、scratch 隔离和行 mask。把白名单暂收窄到 c11，因为它的 L2 工作集估算最宽松；移除“只有 call≥2 才正确/才启用”的语义依赖，至少在本地可控 harness 上验证 call 1、2、3~5、6+ 与随机合法 shape。

通过后才做平台候选/锚分块评测。c4 工作集贴 50 MB，c3 估计约 103 MB，应分别作为后续实验，不能一次全开后用总 `Σtk` 判读。旧 `+0.67~0.72 raw` 不作为晋升预期。

### 3. c5/c7 的 judge-side 分段计时/加倍探针

这两案曾被估为逐案理论缺口较大，但缺少当前底盘上 md、dn、aux 的独立分解。P1 当前不支持官方 custom test，因此使用正式提交中的“纯函数阶段重复一次，以 `Δtk` 估阶段成本”的诊断方式，或在非官方 sandbox 做初筛后由平台闭环。探针必须保持输出、输入和语义不变，不能利用未检查调用或缓存答案。

目的不是再做微调，而是先确定是否存在 ≥0.3 ms 的单一结构块。若没有，就不再从旧标定模型臆测可回收量；若有，再针对该阶段生成一个结构候选。

## 9. 交给下一执行代理的硬约束

1. 任何新候选都必须对题面全部合法输入正确；`_KNOWN12` 只能用于优化白名单，不能把其他输入当成无需正确的“隐藏调用”。
2. 禁止利用验证器盲点、只在未检查调用改错输出、缓存 hidden-state 相关结果、操纵计时口径或碰 `tb` 抽签。
3. 静态权重预处理允许，但只缓存由 `gate_weight`、专家权重、`topk` 导出的数据，并正确处理测试点切换。
4. 源码哈希与 testcase key 只作标识关联，不推断输入种子。
5. 性能判断使用逐案 `tk`、机器状态回归和分块重复；raw/display 不用于晋升。
6. 每个候选保存：源码哈希、SID、12 案 `tk/tb/score`、双 oracle SQNR、日志阶段、触碰 case 和锚 SID。
7. P1 使用 distributed Triton 3.4.0，暂不支持官方 custom test；其他 sandbox 只作筛选，不能冒充官方验证。
