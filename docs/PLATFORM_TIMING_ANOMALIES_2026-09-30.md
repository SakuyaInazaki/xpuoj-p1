## 1. 样本范围与定义

- 按本账号 P1 `querySubmissions` 的 `maxId` 连续分页到 SID <149480；保留该界限以上全部记录，没有按得分选样。现存最早为 149486，最新为 151808。
- 187 发分为 **125 AC、34 WA、21 Canceled、7 TLE**。125 发 AC 均有完整 12 案计时。
- 极低值定义：该 testcase `status=Accepted`、`pass=true`，且 `tk < 当前 v926 对应案正常参照的 50%`。此门只捕获明显异常，不把百分之几的改善归入异常。这里把 50% 改成 80% 得到相同的 9 发名单。
- 9 发包含至少一个通过检查的极低 testcase，其中 7 发整题 AC，另 2 发因其他案失败为 WA。失败 testcase 的 `tk=0/pass=false` 单列排除，不能算成功获得零时间。
- 首次/重复只依据这段完整记录中的 **整份源码 SHA**。不是全比赛第一次提交、首次 kernel 特化、同一 worker 的缓存冷暖或物理机器身份。

新候选同时改变代码、编译工作量、提交时刻与可能的 worker，因此不能从这张表推出因果或未来概率。不得把 12.1% 代入独立抽奖公式保证“发若干次必出”。

## 4. 机制假设，按当前证据排序

| 假设 | 当前支持 | 缺少什么，如何辨别 |
|---|---|---|
| 新源码/新特化与采集启停、模块加载生命周期相互影响 | 所有 7 个完整 AC 事件都在首次 SHA；同码后续恢复 | 缺 JIT cache 命中、编译阶段、worker 身份；用第 6 节区分仅整文件 SHA 改变与 JIT 函数源码改变 |
| 部分 activity 或时间戳漏收/错误归属 | 明显档位、约 1/3 残余、零时间同时正确性通过 | 缺有效 kernel 条数、无效 timestamp 数、dropped records、逐 rank 汇总；应由平台暴露这些诊断 |
| 固定扣除或跨阶段时间归一化错误 | c11/c12 的约 0.10 ms 同步减量 | 没有计时器源码；与整阶段漏计都能解释部分现象 |
| 某类 worker/机器的采集配置不同 | 正常/异常交错可能是调度结果 | 只有任务 UUID，没有 worker/GPU/版本身份；UUID 不能当机器 ID |
| 真实代码加速或普遍“热机” | 无法解释同码从零恢复、多个版本相同低值档位 | 目前证据较弱，不据此修改正常性能判断 |

**特别要核查延迟 JIT：** 现役 `_CALLN` 在前两次与后续调用选择不同计算图。题面只保证至少一次预热，不能排除某个 FP8 特化第一次实际执行发生在之后的计时/检查过程。新函数源码可能需要临时编译，而同码后续运行命中外部缓存。这与“首次 SHA”关联相容，但不知道评测器真实预热次数、模块生命周期和缓存位置，因此仍是假设。诊断时不能把首次整文件 SHA 直接标注为冷 JIT。

本地旧比赛调研称使用 CUPTI，但其描述带 B/C 待核实标记，当前公开题面/最新答复没有给出采集器实现。NVIDIA 的 [CUPTI 12.8 官方 API 文档](https://docs.nvidia.com/cupti/12.8/api/group__CUPTI__ACTIVITY__API.html)说明：活动记录可能因缓冲不足丢失，部分记录可能出现无效零时间戳；[官方 tracing 教程](https://docs.nvidia.com/cupti/tutorial/tutorial.html)展示了异步回调和结束 flush。**这些是候选故障机制，不证明 XPUOJ 使用该版本或遭遇该故障。**

这里只研究平台返回的事实和正常完整计算的复现性；不修改计时器、不伪造 metrics、不通过延迟完成/返回旧结果制造漏计，也不故意耗尽 profiler 缓冲。这样的做法既无法提供可靠机制证据，也会破坏评测合同。

## 5. 异常可以贡献多少榜分

最佳 SID149493 不只是 c11/c12 低 tk：c5 的 **tb=48.349 ms**，同窗正常参照约 **12.720 ms**；该案 q 因而达到 94，正常参照为 81。还含其他 tb 偏移。

使用同窗 11 发 v842 的逐案中位 tb，和 c11/c12 正常 tk=0.899/1.497 进行条件替换：

| 对 149493 的条件模型 | raw |
|---|---:|
| 实际记录 | 85.17 |
| 只把 c11/c12 tk 换回正常参照 | 83.25 |
| 只把各案 tb 换回同窗中位数 | 83.92 |
| 两者都替换 | 81.92 |

这是归因用的条件模型；参照并非 149493 的同 SHA 复测，且取整和分母变化存在交互，不能把差值当独立因果贡献相加。它清楚说明：**最高分来自 tk 异常和 tb 抬高的叠加，不能只复刻 c12=0 就期待刷新 85.17。**

固定当前 v926 的正常 tb、其他案 tk，用已观察的 `th=0` 评分段计算：

| 假设哪些案 tk=0 | 条件 raw |
|---|---:|
| 仅 c12 | 83.17 |
| c11+c12 | 84.33 |
| c10+c11+c12 | 86.17 |
| c9+c10+c11+c12 | 88.25 |

因此，就算目前出现过异常的 **c10–c12 三案同时全部为零**，在当前固定 tb 模型下也只有 raw 86.17。raw90 需要更广范围的异常、tb 抬高和/或真实优化叠加；本段没有 c1–c9 极低 tk 的实证，不能承诺扩展。这个结论比“继续碰异常直到 90”更适合分配剩余时间。

## 6. 下一轮可直接执行的异常诊断小批次

先验证 **源码身份改变** 与 **JIT 函数源码改变**，不混入新的优化算法。由用户指派的唯一平台执行者完成，固定 6 发上限，不把它扩成无期限重复提交。

| 标签 | 具体文件与变化 | 控制的因素 |
|---|---|---|
| A | `p1/references/kernel_v926_measured.py`，SHA `2633cc995eb2…` | 已测同码锚 |
| B | 从 A 生成独立候选，只添加一行固定的**模块顶部注释**；JIT 函数内部文本不变 | 整份提交 SHA 改变；预期不改变函数源文本，但平台是否按整文件缓存未知 |
| C | 当前 `p1/kernel.py` 清理版，SHA `eb5ffee8db40…` | 保留函数 AST/计算一致，但函数注释文本、定义集合改变，可能影响 JIT/cache；同时完成原本需要的清理版确认 |

顺序预先冻结为 **A–B–C–C–B–A**，全程一个在途任务。B 在两次提交间逐字节不变，C 也不再改动。保留所有正常、异常、失败结果，不只留最高分。B 必须与 A 的完整模块 AST 相等；C 使用已有保留函数 AST 证明。所有版本每次计算当前输入的完整输出，启动参数与数学不变。

解释结果：

1. 若 B 首次异常、同码重复正常，而其 JIT 函数文本与 A 相同，则整文件身份/作业分配链值得继续查；仍不能直接认定 JIT 冷编译。
2. 若只 C 首次异常，则 JIT 源文本/编译集合变化更可疑；C 同时改变多个编译相关因素，尚不能锁定单一原因。
3. 若 A/B/C 都正常，结束这条小批次。六发全正常并不统计否定低概率事件，但没有理由立刻扩大为数十发。
4. 若同码连续异常，先记录这是与既有 0/67 重复 AC 不同的新证据，核对当前平台、机器信息和正确性，再决定一对独立确认；不要直接当生产提速晋升。
5. 任一 TLE/WA 保存日志并停止该变体；500 秒为整批预算。不得把失败零时间计入命中率。

这六发是建议的诊断预算，**本轮未生成 B、未提交该批次**。也可以把 C 的第一次确认和 A 的正常对照并入原有必要验证，减少总额度。不要额外要求本地 GPU；单卡 custom 不能替代这组 P1 四卡评测器复现。

若获得新的合法诊断能力，优先要平台提供：每案每 rank 的实际调用/预热次数、是否在计时区间编译、有效 kernel 记录数、零时间戳/丢记录数、计时区间和 flush 边界、worker/驱动/CUPTI 版本。没有这些时，不用沙箱绕过手段读取内部状态。
