## 3. 题意和线上能力：采用什么、不再假设什么

每 rank 的本地输入是 `X[T,H]`，权重提供该 rank 的 `E/4` 个专家，router 在四卡相同。路由先做 BF16 投影并按 BF16 保存 logits，再进行 FP32 softmax、top-k、归一化。每个分支为：

```text
g = BF16(x Gᵀ), u = BF16(x Uᵀ)
a = BF16(w · SiLU(FP32(g)) · FP32(u))
c = BF16(a Dᵀ)
output = BF16(按原 token 合并各 c 的 FP32 和)
```

FP8 是允许误差范围内的实现选择，并非把题意改成 FP8 oracle。正式要求为 SQNR ≥22 dB、输出有限且完整、输入只读、相同输入独立调用逐字节确定。静态权重和 topk 可在预热预处理；**X 会在预热后更换**，路由、ACT 和结果必须来自本次 X。切换测试点后静态权重可能变化。[完整题面](1-full.md)

## 4. v890 的有效计算路径

全部 12 个正式形状都进入 replicated 路径：**预热收集全专家权重，每卡只处理本卡 token，稳态无 token 跨卡通信。** 不能把它误描述成“每卡重复算了其他三卡 token”，也不能在优化预算中再减掉一笔已经不存在的 dispatch。

```text
预处理：收集静态专家权重 → FP8/scale/物理布局缓存
本次 X：router → 稳定 expert 排序、ORDER/INV/metadata → X 量化
       → MD(gate+up+SwiGLU+route weight+ACT FP8)
       → DN(Down FP8 与输出 scale)
       → 按原 slot 顺序 gather/sum → BF16 output
```

| 家族 | 有效工作特征 | 已经在生产的机制 |
|---|---|---|
| c1/c2 | E=8、平均 4096 branches/expert、I 很长；有用 FLOPs 最大 | FP8 GU/DN、交错 GU、融合 ACT 量化；继续压寄存器或加 stages 不是新的算法 |
| c3–c8 | 中等专家数与行数，计算和中间数据流量共同决定性能 | padded DN、direct INV_PAD；c3/c4/c6/c8 为静态 DN scale，c5/c7 仍动态 |
| c9/c10 | E=256、平均仅 128 branches/expert、权重 6/4.5 GiB | 物理 tile 连续 GU/D 权重、packed compact sort、compact DN |
| c11/c12 | T=65536、k=2、H=1024；归并流量相对更显著 | 短 K 的 TMA MD、padded static DN、direct INV_PAD |

静态 DN 的当前系数是 **1.02×L1 界**。offsets→PAD_DELTA 融合也已完成；这两项不再作为待实现方向。

## 5. 最近实验的真正结论：替代旧交接的优先级

### 5.1 EP2 已修好，但没有净收益

| 方案 | SID | c9 / c10 tk，ms | 结论 |
|---|---:|---:|---|
| v905：修 metadata、scatter 代替被拒的 cumsum | 150964 | 2.843 / 2.441 | AC；旧 world all-gather 包装仍很慢 |
| v906：single-peer direct put | 150965 | 2.705 / 2.310 | AC；通信改进有效，但整案仍输 v890 |
| v914：sentinel sort、固定尺寸改造 | 151061 | 2.946 / 2.047 | AC；c9 更差；未改 c11/c12 同时出现快值，不能把窗口归因于候选 |
| v930：pair MD BM256/BN64，DN 保持原 tile | 151332 | 2.950 / 2.737 | **AC 而明显慢**；“BM256 只差编译跑通”已经不是事实 |
| v890 描述性基准 | 本文六锚 | 2.443 / 1.8885 | 无动态 token 通信 |

EP2 使每 owner 的权重容量减半，不保证每次 GEMM 的 B 读请求减半，更不保证 HBM 流量减半。每专家行数增加也增加 row tiles；缓存命中、padding、两卡等待、辅助排序与返回通信都必须计入。旧“BM256 是唯一能减少 B HBM 的办法”属于过强推断，不能照抄为定理。

**决策：本次冲刺不再给 EP2 分配实现预算；TP2 同样不作为备用主线。** TP2 旧 145084 负结果尚未被新正证据推翻，且多了 partial 流量。只在有独立完整计算子链节省足以覆盖真实 peer 成本时重开，不能把修同步当成进展指标。

一次单案 +1 整数分，只给整题 **1/12≈0.0833 分**。升档时间为 `tb·(100/(q+1)−1)`。c10 门槛从旧模型的约 5% 变到本表 0.24%，来自基准选择与区间边界变化，不代表代码突然产生了新收益。

| 冻结本节 tb 的条件情景 | 模型 raw | 相对模型基线 |
|---|---:|---:|
| c11/c12 各降 5% | 82.00 | +0.17 |
| c11/c12 各降 10% | 82.08 | +0.25 |
| c9/c10 各降 30% | 82.75 | +0.92 |
| c9/c10 各降 50% | 83.50 | +1.67 |
| 全案各降 30% | 86.42 | +4.58 |
| 全案各降 50% | 89.75 | +7.92 |

在这个固定模型中，同百分比降时达到 raw 90 需约 **51.11%**；不是说每个案都必须降这么多，而是说明目前没有一两个小改动能闭合总账。即使理想地把 c1/c2/c9/c10 时间全部设为零、其他案不动，当前分支模型也只有 raw 89.33。

每卡有用专家 FLOPs 约 `6T k H I`，权重 FP8 容量约 `3EHI` 字节。容量不能当 HBM 实测流量；tile 重读可被 L2 命中，也可能放大实际流量。c1/c2 已有用整链吞吐约 1.43/1.47 PFLOPS；若要求它们单案都 q=90，需约 3.36/3.62 PFLOPS。没有新计算机制或同栈测量证据，不能承诺靠配置微调达到。

结论是**保留用户目标，诚实执行有证据的最大化**。不降低官方当前成绩，不把模型进步伪装成榜面进步，不把仅能解释 0.2 分的路线描述成 4.83 分突破。

## 7. A：k=2 按 slot 分组，让最后一条 DN 直接完成归并

### 7.1 设计选择

当前 c11/c12 的 DN 先写两份 FP8 branch 输出，fin 再读两份并写最终 BF16。改成：

```text
本次 router
  → 按 (slot, expert) 稳定排序，仍是同一个 2T branches 的排序
  → MD 输出同布局的 compact ACT / A_scale
  → DN0：只算 slot 0，写 padded FP8 D0 + S0
  → DN1：只算 slot 1，在 epilogue 中读取该 token 的 D0/S0
          形成 q0*s0 + q1*s1，唯一写入 output[token, h]
```

使用当前 stream 的两次有依赖 launch 保证 DN0 完成后 DN1 才读。无需浮点 atomic、跨 CTA 自旋或跨卡协议。DN0+DN1 **两次 launch 替换当前 DN+fin 两次 launch**，不把减少 launch 数写成收益来源。

**第一版保留两分支当前的 FP8 量化/反量化数值链。** DN1 的 q1 在寄存器中转 FP8 后再转 FP32，无需落盘；不要同时删掉 q1 量化或改变 BF16 舍入位置。算法通过后才单独讨论更高精度 epilogue。

### 7.2 为什么不直接把两分支依次写 BF16 output

忽略 padding、scale 和 metadata，每 rank 的逻辑字节账是：

| 实现 | scratch 写/读 + 最终输出字节 |
|---|---:|
| 现役 k=2，FP8 Down + fin | `2TH + 2TH + 2TH = 6TH` |
| 先写 BF16 分支 0，再读出加分支 1 | `2TH + 2TH + 2TH = 6TH` |
| **FP8 D0 暂存 + DN1 融合** | `TH + TH + 2TH = 4TH` |
| 两专家 DN 全部在一个 CTA 内归并 | `2TH`，但有 pair 分组代价 |

c11/c12 的 `T=65536,H=1024`，A 方案从 **384 MiB 降到 256 MiB**，少 **128 MiB**，是本段流量的 1/3；**不是整个算子的 1/3**。若有效带宽取 1.5–3 TB/s 做敏感性分析，纯字节项相当于约 45–90 µs，未扣新增排序成本、输出散写和计算 padding。该范围是预算，不是测量。

另起一个 ACT 重排 kernel 会新增 `2·(2T)·I` 字节：c11 是 **256 MiB**，c12 是 **512 MiB**，会吃掉预算。因此直接让排序、输入量化、MD 的行顺序成为 slot-major，**不要在 MD 后再搬一次 ACT**。

### 7.3 精确索引合同

令 `b=2*t+s` 为原分支编号，`s∈{0,1}`，路由专家为 `e=flat_ids[b]`：

```text
group = s*E + e                 # 0..2E-1
expert = group % E              # 用于 GU/D/BNORM/weight scale
slot = group // E               # 用于 DN0/DN1 分段
ORDER[r] = b                    # compact group-major row -> 原分支
INV[b] = r                     # 原分支 -> compact ACT row
COUNTS[group]                   # 此 group 的实际行数
```

排序输入规模保持 `2T`，组数由 E 变成 2E。第一版可以生成一次 int32 `group_ids`，复用现有 counting sort；不要为了少一个轻量 kernel 先改 router 的数值计算。后续只有测到可观排序成本才把 group key 生产融合进 histogram/scatter。

**MD 必须区分 group 与 expert：** counts 和 row-start 用 group；权重指针、B scale、BNORM 用 `group%E`。`_prepare_moe_metadata` 的组数传 `2E`，MD 仍计算原 E 个专家的权重，绝不能把 `G=2E` 当权重维度。现有 c11 的 `_gq1p_tm` 使用新的 INV，即可直接生成相同 compact 顺序的 A；`w_sorted = flat_weights[ORDER]` 也跟随新排序。

DN0/DN1 可以共享一套全局 group metadata，使用 GPU 生成的 tile 前缀分界，不 `.item()` 回传边界：

```text
slot0_tiles = Σ_{g < E} ceil(COUNTS[g]/128)
slot1_tiles = Σ_{E ≤ g < 2E} ceil(COUNTS[g]/128)
```

需要区分 global tile index 与 slot-local tile index。DN1 访问 metadata 使用加上 `slot0_tiles` 的 global pid；DN0 的暂存 row 使用 slot0 的 padded row。每个 tile 的 compact row begin 仍须取 per-tile 数组，不用 per-group 起点按 pid 索引。

只为 slot0 维护：

```text
P0[t] = padded row of original branch b=2*t
```

DN1 从本行 `b=ORDER[r]` 得到 `t=b//2`，用 `P0[t]` 取 D0 和 S0。**P0 不能拿来索引 ACT**；ACT 使用 compact r。可以复用 group-major INV_PAD 的偶数分支部分，因为 slot0 排在前面，slot0 padded 行从零开始。

在 `tl.swizzle2d` 之后再得到本 CTA 的实际 `local_m,pid_n`，然后构建 compact/padded/output 地址。不能用 swizzle 前的 N=0 判断决定唯一 metadata 写者。

### 7.4 容量与唯一写者证明

每 slot 恰有 T 个分支。BM=128 时，slot0 的安全行容量可取：

```text
P0_cap = round_up(T + E*(128-1), 128)
c11/c12: P0_cap = 69632 rows
```

所有空 expert 的 counts 允许为零；不要按平均 `T/E` 分配。无效 padded 行可不清零，但读写 mask 和 P0 必须保证它们不被当有效输出读取。

每个 token 在 slot1 中恰好出现一次；N 维 tile 分割不重叠，因此每个 `(token,h)` 恰有一个 DN1 写者。DN0 不读前一轮 output，DN1 只读本次 DN0，重复调用不用依赖残留数据。使用固定容量缓冲可以避免动态 shape 特化，但必须每次重建 counts/ORDER/P0。

对每个 expert，有：

```text
ceil(n_e0/128)+ceil(n_e1/128)−ceil((n_e0+n_e1)/128) ∈ {0,1}
```

因此相对 expert-only 分组，最多多 E 个 tile；c11 每卡最多额外 4096 个 padded branch rows，约有用行数的 3.125%。这是 padding 上界，不是耗时上界；tile 次序改变仍可能影响 L2。

本轮 CPU 验证覆盖 **35 种场景、466,432 条分支**：空组、63/64/127/128/129/255/256/257 边界、随机路由、全落同一专家对、反转 slot、循环路由。覆盖、反向映射、容量和单写者检查通过。给定相同 q/scale、按明确 FP32 乘加舍入模拟的最终 BF16 位模式也相同。

这没有验证 WGMMA 舍入、GPU FMA contraction、TMA、JIT、SQNR 或跨调用行为。[证明脚本](reports/prove_slot_last_dn_20260930.py)、[检查输出](reports/2026-09-30-slot-last-proof.json)。

### 7.5 数值和资源合同

DN0/DN1 都先复用当前 c11 的静态尺度：

```text
q = fp8(acc * folded_D_scale)
s = max(A_scale * C, 1e-12)
v = FP32(q) * s
out = BF16(v0 + v1)
```

当前 fin 没有先把各 `q*s` 舍入 BF16。首版别额外加一个 BF16 branch 舍入，也别改 `max(...,1e-12)`，否则无法隔离布局变化。最终仍对题意的 BF16/FP32 oracle 做验收，不能只和现役误差互比。

保留原 slot0→slot1 的加法顺序。GPU 可能把 `q1*s1+v0` 收缩为 FMA，CPU 证明没有覆盖它；要在合法 custom 比较实际输出，再查差异来源。若与基线不 exact，也不自动等于错误，但候选自身的逐次确定性与独立参考 SQNR 必须通过。

先维持 BM128/BN256/BK128 与当前 DN 主循环。融合 epilogue 增加 D0 load、scale load、整数映射和 BF16 scatter，可能增加寄存器压力；要尽早消费临时 q/scale，避免同时长期保留多块 FP32 tile。不要首版同时加 BM256 或 FP16 accumulator。

DN0 可继续 TMA store 到 padded D0；DN1 对原 token 行做指针 store，行内 H 方向连续，行间分散。这是主要风险之一：**省掉 scratch 并不保证省下的时间能抵消 TMA store 变成 scatter 的代价**。

### 7.6 实现和实验顺序

1. 写独立候选，只触达 c11；基线 SHA 与本页一致。unknown shape 保留完整合法 fallback。
2. 先完成 group/ORDER/INV/P0 的 CPU 合同与 AST 调用检查。不要调用或缓存本轮 X 的历史结果。
3. 若单卡 custom 模式可构造同规模完整链：同样 router 输出/metadata 输入、同样权重和 ACT 工作集，比较“当前完整子链”与“含新增 metadata 的候选子链”；记录其版本，不把 Triton 3.6 的速度外推到 P1。
4. 正式 P1 首筛保留其他 11 案为 v890。本文 c11 下一档门槛约 **0.8486 ms**，继续门取更严格的 **≥3% 全案改善，即约 ≤0.8463 ms**。只改善 0.3% 不值得追加十几对。
5. 若初筛两对均有 ≥3% 信号，独立新一批三对确认，记录原始 tk、全部正确性与异常。若新版本明显慢，最多做一次基于证据的修正；不要转为参数扫表。
6. c11 成立后才扩 c12。c12 I 更大，MD/ACT 权重更高，不能把 c11 百分比直接照搬。c1/c2 最后考虑，长 K 的收益占比小且编译风险高。

## 8. C：专家对 DN 保留为备用，先算代价

对 k=2，将 token 按无序专家对 `(lo,hi)` 分组：

```text
pair_id = lo*(2*E-lo-1)//2 + hi-lo-1
```

c11 E=32 有 496 对，每对平均仅约 132 tokens。一 CTA 计算这对专家的两条 DN 并直接写 output，能删除所有 Down scratch，逻辑上比 A 再省 128 MiB。但必须为每个 token 保留原 slot 与 compact ACT row，最终顺序固定；不能用 Down 的 INV_PAD 去读取 ACT。

本轮在**同一份合成随机路由**上比较：

| 布局 | 等价 padded branch rows | 相对现役 | B tile 访问次数相对现役 |
|---|---:|---:|---:|
| expert BM128 | 133120 | 1.000 | 1.000 |
| slot×expert BM128 | 134656 | 1.0115 | 1.0115 |
| pair BM64，两分支 | 166656 | 1.2519 | 2.5038 |

这里的 B tile 次数是逻辑 GEMM 请求数，不是 HBM 流量。c11 的 D 约 32 MiB，有缓存机会，但不能保证在 ACT 竞争下常驻。pair 方案还会引入两路 ACT gather、pair sorting，以及两份 accumulator 或其等价的生存期压力。

因此 A 优先。只有当 A 的主要问题是两次 DN 调度或 slot-major 额外准备，而 pair 设计能明确解决时再试 C。若 A 因 scatter/store 与额外 epilogue 已明显变慢，C 往往还有同样问题，不能机械地续投。

C 首版只做 c11、BM64、固定顺序、无原子。含 metadata 的完整子链/全案未达到门槛就停止。取消 DN FP8 量化会改数值链，须独立 oracle，不声称与 v890 bitwise 等价。旧 [专家对 CPU 索引证明](reports/2026-09-27-pair-directions-proof.json)可复用思路，不能当 GPU 收益。

## 9. P0：当前代码中必须被单独处理的正确性问题

### 9.1 `_CALLN` 不是静态缓存状态

`run_kernel` 的 `_CALLN` 是进程级累加，未按测试点重置；`_GA` 只在部分形状的 call3–5 开启。源码事实包括：

- router 在 call1、call2、call≥3 走不同实现；
- padded sort/packed sort 在 call≥3 才开启；
- c3–c8 的 call3–5 可能使用 token-only A，call≥6 改回 sorted A；
- ACT 的 BF16/FP8 路径也随调用序号变化。

这些分支可能曾为了分摊 JIT 添加，但题面保证“至少一次预热”，没有给出能依赖的固定调用编号。**相同输入在两种路径中各自重复可确定，不等于跨路径相同输入 bitwise 相同。** 不应以这些编号判断评测阶段或少做本次计算。

目标家族必须列出第 1/2/3/4/5/6/8 次的路由、量化、MD、DN 路径；测同输入重复，以及 `X_A→X_B→X_A`。所有路径都应完整计算当前输入。推荐新设计从第一次调用就采用同一个合法数学实现，静态缓存 miss 仅增加预处理；如果 JIT 总预算不通过，缩减重复实现/特化，而不是假设计时只会发生在某几个调用。

这项修复独立建候选、独立验证，不在 A/B 的性能对比中悄悄更换底盘。不支持“已 AC 所以不用处理”，也不建议不经验证把所有历史分支一键全开。

### 9.2 权重缓存不能只凭 shape 宣称正确

`_get_full_weights`、`_get_full_fp8_weights`、`_get_full_fp8_weights_lowmem_tiled` 等存在 shape-only 键。相同尺寸的新权重会命中旧权重；静态 DN helper 持有 q/scale 引用只能解决自身 id 复用，不能修复上游返回旧 q。

合同边界必须明确：

| 情况 | 必须采取的行为 |
|---|---|
| 同一测试点，只换 X | 复用静态权重；重新算 route/ACT/output |
| shape 不同 | 正确建立新权重和新容量缓存 |
| 同 shape、换权重 tensor | 键包含全部相关输入身份与标量，并持有相应引用；验证包装对象行为 |
| 同 tensor 原地改变权重 | 单凭 shape 或 id 都检测不到；需要官方边界/版本合同、完整内容检查，或重新预处理 |

不要绕过沙箱读取被禁止的 `_version`；抽样 fingerprint 不是完整内容一致性证明。由于 P1 的静态预处理含 collective，**所有 rank 的 cache miss/重建判断还必须一致**：仅一个 rank 失效后单独 all-gather 会挂。若采用“任一 rank 变则全部重建”，相应公共协议和稳态成本也要计入。

题面没有公开跨测试点身份/原地更新的完整约定。当前 v890 只在已有正式样本中通过，并未获上述普适保证。最终交付必须注明验证范围和这个未决合同，不能用“全 12 案 AC”代替它。

## 10. 只用 OJ 的执行流程

### 10.1 本地做静态和数学工作，OJ 做 GPU 判断

本地允许并且应该做：源码 diff、SHA、AST、语法检查、shape/索引/容量/代数证明、读取既有结果、计算评分阈值。它们不需要本地 GPU。

GPU 编译、性能、精度、determinism 依赖正式 P1 或已开放 custom。当前分布式 custom 不可用；单卡 custom 可用性不等于四卡协议通过，也不等于它与 P1 同编译栈。

合法 custom 应完成真实完整任务并写完整输出，保留同样的大权重工作集与每次动态准备；不以小矩阵反复热缓存代表 E256 的 6 GiB 权重。若计时工具被拒，使用平台报告的整 workload 时间做两个等价任务的 A/B；不绕白名单、不伪造 score 输出、不用 early return 跳过计算。

### 10.2 唯一平台操作者

用户负责派发 agent，可以让实现和 CPU 分析并行，但同一时刻只由一个操作者提交 P1。遵循 [提交说明](docs/SUBMISSION.md)：先查当前在途和池水位，冻结文件/SHA，提交后记录 SID，只轮询那个 SID。

本地 poll timeout、Pending、Canceled 各有含义。请求超时不能说明服务端没创建 SID，先只读查询；不重复发。不要取消不属于本轮、来源不明的任务。不修改共享 token pool，不输出凭据。

当前不应使用 `experiments/2026-09-29/serial_window.py` 作为优化驱动：它按分数阈值循环重投同一生产代码，没有独立候选或预注册对照。`batch_v926*.log` 也展示了多个候选连续入队而锚落在末尾的问题。历史结果保留，但这种顺序不能继续当成配对实验。

### 10.3 数据记录与性能判定

每个候选先冻结：父 SHA、候选 SHA、触达 case、改动机制、历史失败前提改变了什么、继续/停止门、最多提交数。

结构候选用 `A→B` 和 `B→A` 两对初筛。A 为同一基线，B 为同一候选。满足预先规定的收益门后，才安排独立确认组；不不断追加直到均值变正。全案都变的候选没有 untouched control，不虚构控制组。

记录平台 `tk/tb/th/displayScore`、SQNR、determinism、sample、终态和错误签名。按日志的 `tc=` 归案，不按字典枚举次序。`userError` 同时兼容字符串及 `{content/data}`；逐案 `score` 可能是正确性分，性能分使用 `displayScore`。

先看原始 tk、配对比和重复分布，未改案帮助判断环境异常。旧 `mnorm.py` 机器签名已有失效记录，不能把回归修正的一个负残差当成晋升依据。`tk=0`、tb 异常或未改案集体断崖应保留并标注，不从候选和锚中不对称删样本。

门槛建议：正式必须 ≥22 dB；研发尽量 ≥22.5 dB，并报告相对 v890 的变化。日志只给两位小数，相同 SQNR 不等于逐字节相同。sample 没有充分日志时写明缺失，不能由 c1–c12 推断覆盖。
